# Phase 0 Research: Application de Despesa Recorrente (Cadastro)

Todas as incógnitas foram resolvidas via clarificação da spec, o refinamento de origem (`refinements/backend/application-despesa-recorrente.md`), a constituição do projeto e leitura do código existente (`backend/Domain`, `backend/Infrastructure`). Não há itens `NEEDS CLARIFICATION` remanescentes.

## 1. `IRepositoryManager`: onde declarar e como conectar

- **Decision**: Declarar `IRepositoryManager` em `Domain/Repositories/IRepositoryManager.cs`, expondo `IRecurringExpenseRepository RecurringExpenseRepository { get; }` (mesma forma da propriedade já existente na classe concreta). A classe `RepositoryManager` já existente em `Infrastructure` passa a implementar essa interface, sem nenhuma outra mudança estrutural (continua usando `Lazy<T>` internamente, per Princípio VII). O Use Case depende exclusivamente de `IRepositoryManager` (injetada via construtor), nunca da classe concreta.
- **Rationale**: Decidido explicitamente na clarificação da spec (sessão 2026-09-04) — resolve a tensão identificada no refinamento de origem entre "Application não pode depender de Infrastructure" (Princípio XI) e "o único ponto de acesso a repositórios hoje é a classe concreta `RepositoryManager`". Colocar a interface no Domain (em vez de no Application) segue o mesmo padrão já usado por `IRecurringExpenseRepository` e é a leitura mais direta do Princípio XI ("Infrastructure implementations MUST be supplied to Application through Domain-defined abstractions").
- **Alternatives considered**: (a) Interface declarada em `Application` (paralela ao padrão adotado para `ICurrentDateProvider`, ver §2) — rejeitada explicitamente pela clarificação da spec em favor de (b) Domain, provavelmente porque `IRepositoryManager` é, na prática, um agregador de contratos de repositório já Domain-defined (`IRecurringExpenseRepository`), então mantê-la no Domain evita duas camadas diferentes definindo "o mesmo tipo de coisa" para os dois casos (repositório vs. port de infraestrutura genérico). (c) Use Case dependendo diretamente de `IRecurringExpenseRepository` (sem um `IRepositoryManager` intermediário) — rejeitada explicitamente na clarificação da spec (pergunta 1), que decidiu manter o `IRepositoryManager` como ponto único de acesso, preservando o papel que a classe concreta já cumpre hoje na Infrastructure.

## 2. `ICurrentDateProvider`: onde declarar (tensão com Princípio XI)

- **Decision**: Declarar `ICurrentDateProvider` em `Application/Ports/ICurrentDateProvider.cs`, com um único método `DateOnly GetCurrentDate()`. Nenhuma implementação concreta é criada por esta feature (a spec Assumptions exclui explicitamente essa implementação do escopo); em testes, um dublê fixo (`FixedCurrentDateProvider`) implementa o port diretamente dentro de `Application.Tests`.
- **Rationale**: A spec (Assumptions) decide explicitamente que este port "é declarado nesta camada [Application] e implementado pela Infrastructure", espelhando a decisão já tomada no refinamento de origem. Como esta feature não conecta nenhuma implementação de Infrastructure a este port (nenhuma "supply" de fato acontece — ver Constitution Check), a leitura literal do Princípio XI ("Infrastructure implementations MUST be supplied to Application through Domain-defined abstractions") não é violada *nesta etapa*: não há Infrastructure implementation sendo fornecida ainda. Fica registrado como ponto a revisitar quando uma feature futura implementar `ICurrentDateProvider` na Infrastructure — nesse momento, será preciso decidir entre (i) mover a interface para o Domain (alinhando com a leitura mais estrita do Princípio XI) ou (ii) tratar esse texto do princípio como não-absoluto e aceitar portas Application-defined implementadas por Infrastructure (que exigiria Infrastructure referenciar Application, uma dependência hoje inexistente).
- **Alternatives considered**: (a) Declarar em `Domain/Repositories/` ao lado de `IRepositoryManager`, tratando-a como "mais uma abstração Domain-defined" — rejeitada por não ser um contrato de repositório nem um conceito do domínio de negócio (data atual é uma preocupação de orquestração/infraestrutura, não uma regra de negócio do aggregate `RecurringExpense`), o que a tornaria um corpo estranho na pasta `/Repositories` e nas regras estruturais do Princípio VI (que reserva essa pasta a contratos de repositório de Aggregates). (b) Use Case chamando diretamente `DateTime.Now`/`DateOnly.FromDateTime(DateTime.Now)` — rejeitada explicitamente pelo refinamento de origem e por FR-007 (tornaria o Use Case não determinístico e difícil de testar, violando Princípio II).

## 3. Conversão primitivo → Value Object e agregação de erros

- **Decision**: Para cada campo do Input, o Use Case tenta construir o Value Object correspondente dentro de um bloco que captura a exceção lançada pelo construtor (tipo base esperado: `ArgumentException`, já usado por todos os Value Objects hoje) e, em caso de falha, adiciona um erro de campo (nome do campo + a mensagem PT-BR da exceção) a uma lista acumuladora — sem interromper a conversão dos demais campos (FR-005). Ao final, se a lista de erros não estiver vazia, o Use Case retorna o Output de falha com todos os erros acumulados, sem chamar o construtor do aggregate nem o repositório.
- **Rationale**: Atende FR-002/FR-005/FR-006 diretamente; reaproveita a mensagem já lançada pelo Value Object (após a revisão PT-BR de FR-016) sem duplicar texto na Application.
- **Alternatives considered**: Validar cada campo com uma regra própria na Application antes de tentar construir o Value Object — rejeitada por FR-014/Princípio XI (Use Case não pode reimplementar regra de negócio já coberta pelo Domain); interromper no primeiro erro (fail-fast) — rejeitada explicitamente por FR-005/User Story 2.

## 4. Categoria, frequência e status: por que checar antes de construir o Value Object

- **Decision**: Para os três campos apoiados por um enum (`category` → `ExpenseCategoryType`, `frequency` → `FrequencyType`, `status` → `RecurringExpenseStatusType`), o Use Case usa `Enum.TryParse` para converter o texto recebido e trata explicitamente o retorno `false` (ou um valor fora do enum definido) como erro de campo *antes* de tentar chamar o construtor do Value Object — usando uma mensagem própria da Application para esse caso específico (ex.: "Categoria inválida.", mesma ideia de mensagem que o Value Object usaria para um valor de enum não definido, mas produzida pela Application porque o Domain nunca chega a ver o valor). Frequência e status recebem o mesmo tratamento por consistência e para evitar a mesma armadilha, ainda que a spec só descreva esse comportamento explicitamente para categoria (FR-004/edge case dedicado).
- **Rationale**: `Enum.TryParse<TEnum>(texto, out valor)` retorna `false` para um texto não reconhecido, mas ainda assim preenche `valor` com `default(TEnum)` — que, para todos os três enums deste domínio (`Housing`/`Monthly`/`Active`, todos o membro `0`), é um valor *definido*. Se o Use Case ignorasse o retorno booleano e apenas repassasse `valor` ao construtor do Value Object, a checagem `Enum.IsDefined` dentro do construtor passaria silenciosamente para qualquer texto não reconhecido, mascarando o erro em vez de reportá-lo (exatamente o cenário que FR-004 e o Acceptance Scenario 3 da User Story 2 proíbem). Checar o booleano de `TryParse` antes de construir evita essa armadilha sem reimplementar nenhuma regra de negócio (a regra "quais valores são válidos" continua unicamente no enum/Value Object do Domain — a Application só decide *se tenta* construir).
- **Alternatives considered**: Repassar sempre o resultado de `TryParse` ao construtor, confiando apenas na validação `Enum.IsDefined` do Value Object — rejeitada por reproduzir a armadilha descrita acima (falso-negativo silencioso para texto não reconhecido). Comparar o texto manualmente contra uma lista de valores válidos mantida na Application — rejeitada por duplicar, na Application, a lista de valores que já vive no enum do Domain (Princípio V/YAGNI e FR-014).

## 5. Data de início (`startDate`): quem valida "é uma data de calendário válida"

- **Decision**: O Use Case interpreta o texto `startDate` com `DateOnly.TryParseExact(texto, "yyyy-MM-dd", CultureInfo.InvariantCulture, DateTimeStyles.None, out valor)`. Um retorno `false` (texto malformado ou data inexistente no calendário, ex.: `2026-02-31` — `TryParseExact` rejeita ambos da mesma forma) vira um único erro de campo para `startDate`, usando uma mensagem própria da Application (ex.: "Data de início inválida."), já que o Value Object `CalendarDate` do Domain é um wrapper fino sobre `DateOnly` e não realiza, hoje, nenhuma validação de correção calendária própria (ver `backend/Domain/ValueObjects/CalendarDate.cs`) — o texto já chega ao construtor do Domain como um `DateOnly` estruturalmente válido ou nem chega, pois a conversão falhou antes.
- **Rationale**: Atende FR-003/edge case dedicado. Não há regra de negócio do Domain sendo reimplementada aqui — `TryParseExact` é responsável apenas por *interpretar* o texto (uma preocupação de conversão de tipos, não de regra de negócio), não por decidir se a data é "aceitável" para o aggregate (essa decisão, quando existir, continuaria no Domain).
- **Alternatives considered**: Usar `DateOnly.Parse` (não exato) e capturar `FormatException` — rejeitada por aceitar formatos ambíguos/diferentes de `yyyy-MM-dd` dependendo da cultura corrente da thread, tornando o comportamento não determinístico entre ambientes (viola Princípio II — testabilidade). Adicionar a validação de "texto bem formado" dentro do próprio `CalendarDate` do Domain (passando a receber `string` em vez de `DateOnly`) — rejeitada por estar fora do escopo desta feature (spec Assumptions: nenhuma alteração de Domain além de FR-015/FR-016) e por misturar uma preocupação de parsing de texto (Application/API) dentro de um Value Object que hoje modela apenas "uma data" (Princípio V).

## 6. Revisão das mensagens de erro do Domain para PT-BR (FR-016)

- **Decision**: Substituir, dentro de cada Value Object e do aggregate `RecurringExpense` (apenas onde já existe uma exceção lançada hoje), a mensagem em inglês por uma mensagem equivalente em PT-BR voltada ao usuário final, sem alterar a condição de validação em si nem o tipo de exceção lançada (`ArgumentException`). Nenhum novo caso de erro é introduzido; apenas o texto muda.
- **Rationale**: Decidido explicitamente na clarificação da spec (sessão 2026-09-04) e exigido por FR-006/FR-016/SC-003 — o Use Case só pode repassar a mensagem do Domain "tal como recebida" se essa mensagem já estiver em PT-BR; manter inglês forçaria a Application a traduzir/duplicar texto, violando Princípio VI ("Outer layers... MUST NOT... translate/rewrite the Domain's message").
- **Alternatives considered**: Manter as mensagens em inglês e traduzir na Application — rejeitada explicitamente pela clarificação da spec e pelo Princípio VI. Introduzir um mecanismo de i18n/resource files no Domain — rejeitada por complexidade desnecessária (Princípio V/YAGNI): o projeto não tem hoje (nem esta feature exige) suporte a múltiplos idiomas, apenas PT-BR.

## 7. Estrutura de projeto e nomenclatura

- **Decision**: Novo projeto de classe `backend/Application/ContasEmDia.Application.csproj` (mesmo padrão de `TargetFramework net10.0`, `Nullable enable`, `TreatWarningsAsErrors true` de `Domain.csproj`), referenciando apenas `ContasEmDia.Domain`; e `backend/Application.Tests/ContasEmDia.Application.Tests.csproj` (xUnit, mesmo padrão de `Domain.Tests`), referenciando `ContasEmDia.Application` (e transitivamente `ContasEmDia.Domain`). Ambos adicionados à solução `backend/ContasEmDia.sln`.
- **Rationale**: Consistência com os projetos já existentes; o Princípio XI exige a estrutura `/UseCases/<NomeDoUseCase>/` e a nomenclatura `I<Nome>UseCase`/`<Nome>UseCase`/`<Nome>UseCaseInput`/`<Nome>UseCaseOutput`.
- **Alternatives considered**: Colocar o Use Case dentro do próprio projeto `Domain` — rejeitada explicitamente pelo Princípio XI (camada Application é um projeto próprio) e por misturar orquestração com regras de negócio fechadas do Domain.
