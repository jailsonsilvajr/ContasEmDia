# Data Model: Domínio de Despesa Recorrente

**Feature**: `001-despesa-recorrente-domain` | **Date**: 2026-08-29

All names below are in English per project instruction, even though the
spec/domain concepts are described in Portuguese. Every building block lives
under `backend/Domain/` in the folder mandated by Constitution Principle VI.

## Aggregate

### `RecurringExpense` — `/Aggregates/RecurringExpense.cs`

Aggregate root. Represents a bill that repeats monthly (rent, internet,
gym, ...). Owns its `Occurrence` entities; it is the only path through
which occurrences are created or read.

| Property (accessed via method) | Type | Notes |
|---|---|---|
| `GetId()` | `Guid` | Generated internally on construction ([research.md](research.md) §6). |
| `GetName()` | `ExpenseName` | FR-002. |
| `GetCategory()` | `ExpenseCategory` | FR-003. |
| `GetMonthlyAmount()` | `Money` | FR-004. |
| `GetDueDay()` | `DueDay` | FR-005 / FR-020. |
| `GetStartDate()` | `CalendarDate` | FR-006 (source), FR-007. |
| `GetFrequency()` | `Frequency` | FR-008; only `Monthly` accepted this phase. |
| `GetStatus()` | `RecurringExpenseStatus` | FR-009; default `Active` when not set. |
| `GetNote()` | `Note` | FR-010; optional, always a non-null `Note` whose value may be absent. |
| `GetOccurrences()` | `IReadOnlyCollection<Occurrence>` | FR-014; empty or single-item in this feature. |

**Construction** (`public RecurringExpense(...)`, per Constitution VI —
constructor-only creation, no parameterless/object-initializer path):

Parameters: `ExpenseName name, ExpenseCategory category, Money monthlyAmount,
DueDay dueDay, CalendarDate startDate, Frequency frequency,
RecurringExpenseStatus status, Note note, ReferencePeriod
currentReferencePeriod`.

Behavior (FR-011/FR-012/FR-013, FR-021):
1. Assigns `Id = Guid.NewGuid()` and all supplied fields.
2. Computes `startPeriod = ReferencePeriod.FromDate(startDate.GetValue())`.
3. If `status.GetValue() == RecurringExpenseStatusType.Active` **and**
   `currentReferencePeriod >= startPeriod`, generates exactly one
   `Occurrence` for `currentReferencePeriod` (status `Pending`, due date
   derived per FR-006/FR-020, name/category/amount snapshotted from the
   despesa at this moment — FR-015) and adds it to the internal occurrence
   list.
4. Otherwise, no occurrence is generated (FR-012, FR-013).

No other public mutation method exists in this feature: no
`Pausar()`/`Reativar()` (per spec Clarification #1) and no public
"generate next occurrence" method (out of scope; reserved for a future
monthly-generation feature per the spec's Assumptions).

**Invariants**:
- Exactly 0 or 1 occurrence exists after construction (never more) — trivially
  satisfied since construction generates at most one; FR-016's
  no-duplicate-per-competência rule is the general invariant future
  occurrence-generating features must preserve.
- Every `Occurrence` in `GetOccurrences()` belongs to this aggregate only
  (entity is only ever constructed by this aggregate — internal constructor
  on `Occurrence`, never called directly by outside code).

## Entity

### `Occurrence` — `/Entities/Occurrence.cs`

Internal entity. Represents one billing instance of a `RecurringExpense`
for a specific `ReferencePeriod`. Reachable only through the owning
`RecurringExpense` (no independent repository — FR-014, Constitution VI).

| Property (accessed via method) | Type | Notes |
|---|---|---|
| `GetId()` | `Guid` | Generated internally on construction. |
| `GetReferencePeriod()` | `ReferencePeriod` | Competência this occurrence belongs to. |
| `GetDueDate()` | `CalendarDate` | Derived per FR-006/FR-020 at generation time. |
| `GetStatus()` | `OccurrenceStatus` | Always `Pending` when generated by this feature (FR-019). |
| `GetName()` | `ExpenseName` | Snapshot of the despesa's name at generation time (FR-015). |
| `GetCategory()` | `ExpenseCategory` | Snapshot (FR-015). |
| `GetExpectedAmount()` | `Money` | Snapshot of despesa's monthly amount (FR-011, FR-015). |

**Construction**: `internal Occurrence(ReferencePeriod referencePeriod,
CalendarDate dueDate, ExpenseName name, ExpenseCategory category, Money
expectedAmount)` — `internal` visibility enforces that only code inside the
Domain project (i.e., `RecurringExpense`) can construct one; status is
fixed to `Pending` inside the constructor (FR-019), not a parameter.

**Invariants**:
- Always belongs to exactly one `RecurringExpense` (no independent
  existence — FR-014).
- Display data (name/category/expected amount) is frozen at generation time
  and does not change if the parent despesa's data changes afterward
  (FR-015) — this feature has no despesa-edit operation, so this is
  currently structural rather than actively defended, but the entity holds
  its own copies rather than a reference back to the aggregate, which is
  what makes the guarantee hold once edit operations exist.

## Value Objects — `/ValueObjects/`

All Value Objects are immutable (no state changes after construction),
validate their invariants by hand inside the constructor (no validation
libraries — Constitution VI), and expose their underlying value via
`GetValue()`.

| Value Object | Wraps | Validation | Used by |
|---|---|---|---|
| `ExpenseName` | `string` | Non-null, non-empty after trim (FR-002). | `RecurringExpense`, `Occurrence` |
| `ExpenseCategory` | `enum ExpenseCategoryType { Housing, Services, Transportation, Subscriptions, Other }` | Must be a defined enum value (FR-003). | `RecurringExpense`, `Occurrence` |
| `Money` | `decimal` | `> 0`, at most 2 decimal places (FR-004). | `RecurringExpense.MonthlyAmount`, `Occurrence.ExpectedAmount` |
| `DueDay` | `int` | `1..31` inclusive (FR-005). | `RecurringExpense` |
| `CalendarDate` | `DateOnly` | Any valid `DateOnly` (no extra domain rule beyond being a real date). | `RecurringExpense.StartDate`, `Occurrence.DueDate` |
| `ReferencePeriod` | `(int Year, int Month)` | `Month` in `1..12`, `Year > 0`; comparable (`IComparable<ReferencePeriod>`); factory `FromDate(DateOnly)`. | `Occurrence.ReferencePeriod`, creation-time `currentReferencePeriod` input (FR-021) |
| `Frequency` | `enum FrequencyType { Monthly }` | Must equal `Monthly` — any other value rejected (FR-008, edge case list). | `RecurringExpense` |
| `RecurringExpenseStatus` | `enum RecurringExpenseStatusType { Active, Paused }` | Must be a defined enum value; caller controls default-to-`Active` (FR-009) at the call site, not inside the VO. | `RecurringExpense` |
| `OccurrenceStatus` | `enum OccurrenceStatusType { Pending, Paid }` | Must be a defined enum value. | `Occurrence` (always constructed as `Pending` in this feature). |
| `Note` | `string?` | No validation — free text, may be absent (`null`) (FR-010). | `RecurringExpense` |

Due-date derivation logic (FR-006/FR-020) lives on `DueDay`/`CalendarDate`
collaboration inside `RecurringExpense`'s occurrence-generation step:
`day = min(dueDay.GetValue(), DateTime.DaysInMonth(period.Year,
period.Month))`, then build the `CalendarDate` for that year/month/day.

## State / transitions

Per spec Clarification #1, this feature implements **no status-transition
methods**. `RecurringExpenseStatus` and `OccurrenceStatus` are fixed at
construction time:
- `RecurringExpense.Status` is set once at construction (`Active` or
  `Paused`) and never changes within this feature's scope.
- `Occurrence.Status` is always `Pending` when created by this feature
  (never `Paid` — FR-019).

A future feature that adds transitions (e.g. `Pausar()`/`Reativar()`, "mark
as paid") MUST preserve the invariant that existing `Occurrence`s are
unaffected by a status change on their parent `RecurringExpense` (spec
Assumptions, FR-018).
